# Project Online to Altus Migration References

## Repository boundary

This directory is a reference and debugging catalogue. It is not the operational migration toolset.
The scripts, commands, URLs, identifiers, and procedures mentioned in the source documents must not
be run from this checkout. Use the current approved tools and instructions in the
[Altus Partner Portal](https://partners.altus.pro) for operational migration work.

Use this index to locate guidance, understand scope, prepare questions, and diagnose issues. Keep all
support material sanitized: do not add customer data, exported project files, tokens, secrets,
connection strings, private URLs, binaries, packages, or generated migration output.

The source documents have different versions and dates. Treat the current Partner Portal material and
the implementation team's direction as authoritative when they differ from a document in this folder.

## Migration lifecycle

Use the references in this order when reconstructing the delivery flow:

1. **Kickoff and governance** - confirm scope, assumptions, roles, communications, milestones, and client dependencies.
2. **Technical readiness** - prepare accounts, licences, environments, permissions, software, SharePoint access, and Project Desktop prerequisites.
3. **Scope and configuration** - agree volumes, data choices, financial categories, departments, project types, stage gates, fiscal periods, calendars, security, and field mappings.
4. **Project Online export** - identify the source projects, resources, lookup tables, schedules, and custom fields to retain.
5. **Project and resource import** - create or match Altus bookable resources and projects, then load the agreed mappings.
6. **Task and schedule migration** - choose the task custom-field route, publish schedules, preserve baselines and rates where supported, and migrate calendars and exceptions.
7. **SharePoint migration** - move risks, issues, custom lists, documents, metadata, version history, and folder structures to an approved target.
8. **UAT and issue resolution** - test in the agreed environments, log issues in the shared Teams site, observe the change freeze, and resolve according to priority.
9. **Post-migration validation** - complete ownership, resource, project type, stage, schedule, dependency, register, document, and Teams checks.
10. **Training and support** - deliver role-based training, complete go-live activities, and use the one-week priority support period.
11. **Remigration or diagnosis** - where required, follow the remigration guidance or use the troubleshooting and FAQ references to form a focused support question.

## Important scope and constraint reminders

These points recur across the references and are useful when triaging a question:

- The documents describe Project Online as retiring on 30 September 2026, including its PWA access,
  integrations, and project subsites.
- The standard migration scope covers projects, enterprise resources as Altus bookable resources,
  schedules and tasks, resource rates, baselines, SharePoint risks and issues, custom lists where
  extended, and project documents.
- Workflow history, Project Online timesheet records, and Portfolio Analyses are described as not
  migrated by the standard process. Workflow stages and portfolio analysis may need post-migration
  recreation in Altus.
- Master schedules are not supported as a direct migration target; individual schedules need separate
  treatment.
- Custom fields with formulas require manual recreation after their referenced fields exist. Project
  descriptions may also require manual migration.
- Assignments depend on matching users in the target Dataverse System User table. Missing users can
  result in missing bookable resources and unassigned tasks.
- Non-text lookup-table data may not be emitted by the Microsoft export and may require manual handling.
  Hierarchical lookup tables are supported by the scripts but do not display as a tree in Power Apps.
- Exported schedules use `.MPP`; other migration data is exported as `.JSON`.
- SharePoint document migration can preserve files, folders, metadata, and version history, but the
  references state that permissions, site structure, content types, workflows, retention policies, and
  site columns are not fully migrated by the scripts.
- Timesheet history is handled through the protected-actuals approach rather than bulk migration of
  timesheet records. Confirm the chosen approach before changing how users record actuals.

## Triage notes for agents

When answering a migration question, identify the phase, source data type, target Altus area, and whether
the user needs a decision, a mapping explanation, a validation step, or a fault diagnosis. Start with
the narrowest reference above, then check the detailed manual or FAQ for constraints. Do not infer that
a script name in a PDF means a runnable script exists in this checkout, and do not ask the user to
upload unsanitized customer exports or logs.
